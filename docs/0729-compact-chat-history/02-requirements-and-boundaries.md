# 02. 需求与功能分析

## 1. 用户目标

当 Scroll 会话发生一次或多次上下文压缩后，用户离开并重新进入该会话，页面仍应按原始时间顺序展示：

1. 被压缩驱逐的完整历史消息。
2. Scroll 生成的 `[context compressed]` 压缩提示。
3. 当前模型上下文中的最近消息尾部。

压缩提示作为归档历史与当前上下文的可见边界。

## 2. 功能需求

### FR-1 完整展示

对于带有效 Scroll checkpoint 的会话，`GET /chats/{id}` 返回 checkpoint 覆盖的全部可用归档消息和当前上下文。

### FR-2 顺序与结构

- 归档消息按 `seq` 升序。
- 压缩提示位于归档消息之后、当前尾部之前。
- 用户、助手、工具调用、工具结果及媒体引用保持现有 HTTP `Message` 结构。
- 不重复返回同时存在于历史库和当前尾部的消息。

### FR-3 策略边界

- Scroll：启用完整展示恢复。
- Native 或无法证明为 Scroll 的快照：保持现有行为。
- 以持久化 checkpoint 为判断依据，不以当前配置字符串作为唯一依据。

### FR-4 兼容性

- 保持 `GET /chats/{id}` 的 URL、请求参数和 `ChatHistory` 响应结构不变。
- 前端无需感知 `history.db`、Scroll index 或 SQLite `seq`。
- 不要求 AgentScope Runtime WebUI 新增接口。

### FR-5 降级

以下情况不得导致会话页面不可用：

- `history.db` 不存在。
- SQLite 无法只读打开。
- Scroll checkpoint 缺失、字段损坏或版本未知。
- 某些索引范围已被 retention 清理。
- 某些归档行无法反序列化。

发生上述情况时记录可诊断日志，返回能安全恢复的消息；最差退回当前 GET 的压缩提示与尾部。

## 3. 非功能需求

### NFR-1 模型上下文隔离

展示恢复只能创建临时响应消息，禁止：

- 修改 `AgentState.context`。
- 修改 Scroll checkpoint。
- 写回 session JSON。
- 写入或修复 `history.db`。
- 触发 session save。

因此恢复出的完整历史不会发送给模型，也不增加模型 token。

### NFR-2 只读可靠性

展示读取使用 SQLite read-only URI。不能复用会自动建表、迁移或隔离损坏文件的 `HistoryStore` 写路径。

### NFR-3 性能

本次不预先引入服务端分页。必须增加 20MB、30MB、50MB 全量历史规格，测量：

- GET 完整响应耗时和峰值 Python 内存。
- 前端 `convertMessages` 转换耗时和 Node heap 变化。
- Chromium 页面从导航/会话请求开始到最新消息可见的耗时、JS heap 和错误状态。

DOM 中仍只展示当前 10 条历史消息。

### NFR-4 多会话

测试需确认：

- 会话列表不会携带完整消息正文。
- 切换会话不会出现空白页或无限加载。
- 大会话进入现有转换缓存时，内存增长可测量并在验证报告中说明。

本次不先修改缓存策略；只有测量表明缓存导致显著保留内存时才增加字节预算或绕过大会话缓存。

### NFR-5 可维护性

归档读取、行反序列化和响应组装必须与 FastAPI 路由解耦，可单独测试。只实现 Scroll 所需的最小接口，不创建通用压缩框架。

## 4. 验收标准

### 正确性

- 一次和多次压缩后均能显示完整可用历史。
- 压缩提示只出现一次，位置正确。
- 不恢复 `/clear`、`/new` 之前已脱离当前索引的消息。
- 不跨 session 或 agent 读取消息。
- tool call/result 顺序和前端卡片分组不回归。
- Native 会话响应与修改前一致。

### 性能与稳定性

20MB、30MB、50MB 三档均需输出实际指标。

硬性正确性门槛：

- GET 完成并返回合法 JSON。
- `convertMessages` 完成且结果结构正确。
- 页面能够打开，不出现 error boundary、空白页或进程崩溃。
- 页面历史 DOM 不超过当前 10 条窗口的预期数量。

用于决定是否立即引入分页的测量信号：

- 50MB GET 在本机稳定超过 2 秒。
- 50MB 转换在本机稳定超过 1 秒。
- 50MB 页面稳定超过 5 秒才出现最新消息。
- 50MB 页面稳定保留超过 300MB 的额外 JS heap。
- 从 20MB 增长到 50MB 时，耗时或内存增长超过 4 倍，出现明显超线性。
- 大会话切换后经显式 GC 仍有持续累积，或第二次打开显著恶化。

这些数值用于本次基线决策和报告，不作为跨硬件的严格 CI 性能断言。CI 只断言功能完成、无崩溃和宽松超时。

## 5. 明确不做

- 不新增服务端历史分页接口。
- 不新增游标协议。
- 不修改第三方 AgentScope 分页实现。
- 不为 Native summary 猜测或伪造完整历史。
- 不把恢复的完整历史写回 session JSON。
- 不对旧历史做数据迁移。
- 不删除或压缩 `history.db`。

## 6. 后续分页提示

本项目保留以下明确扩展原则：

> 当前使用 `GET /chats/{id}` 全量恢复 Scroll 历史。只有 20MB、30MB、50MB 基准或后续生产指标证明存在可复现的加载耗时、峰值/保留内存、崩溃或多会话累积问题时，才扩展服务端游标分页；不得仅因理论上的无上限增长提前增加分页状态机。

若触发扩展，优先保持现有 GET 不变，新增可选归档历史分页能力，并同步为 AgentScope 消息列表提供正式的后端分页回调，禁止通过 DOM 监听或私有状态注入实现。
